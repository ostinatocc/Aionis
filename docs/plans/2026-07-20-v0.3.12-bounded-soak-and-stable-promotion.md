# v0.3.12 Bounded Soak And Stable Promotion Plan

Status: fail-closed implementation in progress; v0.3.12 remains an immutable candidate.

## Goal

Turn the published v0.3.12 candidate into evidence for a later stable train
without moving the v0.3.12 tag, changing its publication receipt, or adding an
evaluation framework to the Runtime daemon core.

The stable release is a new commit and annotated tag, expected to be v0.3.13.
It must carry its own same-SHA CI, provider, package, Docker, installer, soak,
and publication evidence. Passing the soak does not relabel v0.3.12 as stable.

## Non-negotiable boundaries

- `src/`, Runtime routes, Runtime configuration, and the daemon entry closure
  receive no soak or release-promotion code.
- The real-Agent harness stays in the external evaluation authority. Runtime
  keeps only generic product APIs and deterministic product gates.
- v0.3.12's tag, digest, GitHub prerelease, notes, and publication receipt are
  immutable historical evidence.
- Stable promotion fails closed. Missing, malformed, mismatched, unverified,
  or non-content-addressed evidence cannot publish `latest`.
- Docker version tags are immutable. Docker `latest` is mutable only during an
  explicitly authorized stable publication after every exact-digest gate.
- Candidate/development release behavior remains unchanged.
- Complexity is paid for by convergence: no Runtime source growth, no workflow
  growth, and no upward reset of the committed ratchet.
- No paid real-Agent run begins until its authority manifest, exact image
  digest, requested model, retry policy, budget, and stop conditions are frozen.

## Task 1: Add stable-promotion authority without growing Runtime

**Files**

- Modify `scripts/ci/release-artifact-gate.mjs`
- Modify `scripts/ci/release-artifact-gate.test.mjs`
- Modify `release-train.json` only on the later stable train
- Add the eventual soak receipt under `docs/releases/`

**Contract**

For `development` and `candidate`, the existing gate result is unchanged and
no promotion authority is accepted as stable proof.

For `stable`, the train schema advances to `aionis_release_train_v2` and the
top-level `release-train.stable_promotion` authority is mandatory. Runtime
contains only the fail-closed adapter and immutable source coordinates:

```json
{
  "schema_version": "aionis_stable_promotion_authority_v1",
  "verifier": {
    "repository": "https://github.com/ostinatocc/AionisRuntime-evals.git",
    "source_ref": "<40-character authority commit>",
    "source_commit": "<same 40-character authority commit>",
    "verifier_path": "scripts/verify-stable-promotion.mjs"
  },
  "candidate_publication": { "path": "docs/releases/v0.3.12-publication-evidence.json", "sha256": "<64 lowercase hex>" },
  "bounded_soak": { "path": "docs/releases/v0.3.12-bounded-soak-evidence.json", "sha256": "<64 lowercase hex>" }
}
```

The Runtime gate verifies that the external authority checkout has the exact
package identity, canonical origin, clean worktree, pinned commit, and regular
non-symlink verifier path. It executes that verifier without provider secrets
and accepts only one exact JSON result bound to the stable Runtime and authority
commits. Missing checkout, non-zero exit, malformed output, or coordinate drift
fails before publication.

For stable verification, trusted Runtime workflow code first validates the
receipt and artifact-manifest paths, raw hashes, harness commit, and exact
pilot/soak/publisher source identities before making any authenticated request.
It uses a dedicated read-only evaluation-repository token to fetch three exact
run/job records, six run-owned Actions artifacts, and six GitHub release assets,
then writes only those sanitized fields to an exclusive owner-only temporary
file. The external child receives that file but not the token, the caller's
home directory, provider credentials, or GitHub configuration.

The external verifier—not Runtime—owns the evidence schema and semantic checks
below. It reads exact raw bytes, verifies both declared hashes, and never trusts
path labels or the authority worktree alone.

The candidate publication receipt must bind:

- schema `aionis_release_publication_evidence_v1`;
- status `candidate`;
- a semantic version lower than the new stable Runtime version;
- a distinct immutable candidate tag and commit;
- exact image repository, release tag, digest, and `linux/amd64` platform;
- successful exact-main CI, protected provider evidence, Docker source run,
  and non-latest GitHub prerelease;
- `latest_promoted: false`.

The soak receipt must bind:

- schema `aionis_release_bounded_soak_evidence_v1`;
- authority decision `pass`, while explicitly carrying no publication power;
- the exact candidate receipt path/hash, Runtime tag/commit, image/digest,
  platform, embedding model/dimensions, requested and returned LLM model;
- a predeclared workload manifest and content-addressed artifact bundle;
- protected pilot, all three soak waves, and a distinct GitHub-hosted protected
  evidence-publisher job;
- six exact-run Actions artifacts and six release assets bound by server IDs,
  hashes, ownership, workflow/job windows, and content-addressed names;
- graceful replacement and SIGKILL replacement recovery;
- offline SQLite verification and terminal worker backlog;
- thresholds and observed metrics, including zero wrong direct-use,
  evidence-backed outcome/feedback/measure coverage, exact replay, and no
  dead-letter/provider-mismatch/exhausted work;
- start/end timestamps and a bounded duration;
- no embedded credential values.

The external verifier also proves that both release tags are annotated, the
candidate commit is on the stable commit's first-parent history, and a
file-by-file allowlist is the complete candidate-to-stable diff. Runtime source,
behavior, dependencies, and lock resolution cannot drift after the soaked
candidate. A behavior or dependency change requires a new candidate and soak;
only explicitly named release metadata, receipts, docs, and release-governance
files may advance into the stable train.

The validator returns only stable publication coordinates; it does not run the
soak or infer success from prose.

**Tests**

- Existing checked candidate still passes with `publish_latest: false`.
- Stable with no authority fails.
- Stable with a missing, dirty, wrong-origin, wrong-commit, or symlinked
  authority checkout fails in Runtime.
- Stable with a non-zero, non-JSON, multi-result, or mismatched external
  verifier result fails in Runtime.
- Stable with missing, permissively readable, symlinked, unbound, or stale
  sanitized workflow evidence fails before publication.
- External tests reject missing/escaping/symlinked evidence and wrong raw-byte
  hashes.
- Stable reusing the candidate tag/version/commit fails.
- Stable with a candidate receipt that claims latest/stable fails.
- Stable with wrong image/digest/platform/provider binding fails.
- Stable with a failed/incomplete soak, wrong thresholds, model fallback,
  missing recovery, or non-zero terminal backlog fails.
- A fully bound stable fixture passes and returns `publish_latest: true`.

**Complexity constraint**

Keep the Runtime adapter small and table-driven. Put the large stable semantic
matrix in `AionisRuntime-evals`. The combined Runtime `scripts/ci` inventory
must ratchet downward; do not raise the budget to fund external evaluation.

## Task 2: Separate immutable Docker tags from mutable latest

**Files**

- Modify `.github/workflows/docker.yml`
- Modify `scripts/ci/release-workflow-contract.test.mjs`

**Behavior**

1. Build once to an immutable build subject.
2. Smoke and recover the exact digest.
3. Inspect the version tag. If it exists at another digest, fail. If absent or
   equal, create/verify it.
4. Only when `release_status == stable` and the release-artifact gate returned
   valid promotion authority, move `latest` to the verified digest.
5. Verify both references after promotion. Never apply the immutable-version
   conflict rule to `latest`.

The mutable `latest` job also requires the protected `stable-release`
environment and a receipt-bound predecessor compare-and-swap. The environment
must be configured before the workflow is enabled; merely naming an
unprotected environment in YAML is not publication authority.

The workflow must expose version and mutable tags separately; it must not parse
an undifferentiated metadata tag list. Concurrency remains serialized by exact
release tag, while stable publication also verifies the observed prior latest
coordinate recorded by the authority chain to prevent an unreviewed overwrite.

**Tests**

- Candidate produces/promotes only the immutable version tag.
- Existing different version digest fails.
- Stable may replace a different `latest` digest only after immutable version
  promotion and valid stable authority.
- Candidate and development can never move `latest`.
- Post-promotion verification checks exact digest for each expected ref.
- Workflow line count does not grow. Remove the Docker metadata indirection if
  needed; labels can be supplied directly from exact release outputs.

**Behavior**

- The checked frozen Create checkout is mandatory for stable and its actual
  `DEFAULT_RUNTIME_REF` must equal the train default.
- Stable fresh-install runs without an explicit Runtime-ref override and proves
  that the installer-selected commit equals the new stable commit.
- Candidate fresh-install may continue to override to its exact candidate tag;
  it is not evidence about the public installer default.
- Do not republish an existing npm version. Publish a new Create version and
  freeze its tag/commit in the new stable train.

## Task 4: Implement the exact-digest external soak authority

This task belongs in a Git-authoritative external evaluation package, not in
`AionisRuntime-focused/src`, `scripts/e2e`, or the daemon image.

The runner must:

- require the fixed v0.3.12 image digest and validate OCI revision/version;
- validate the candidate publication receipt and its checked SHA-256;
- require DashScope `qwen3.7-text-embedding`, dimensions 1536;
- require OpenRouter `deepseek/deepseek-v4-pro` and record both requested and
  returned model; any fallback is a hard failure;
- freeze temperature/top-p/max tokens/timeouts/retries and retry only declared
  transport, 429, and 5xx failures, never semantic failures;
- use real tools plus an outcome verifier, not model self-report;
- checkpoint atomically and resume without duplicate semantic trials;
- retain raw stream/debug/API/operator/flight-recorder evidence with hashes;
- cross-join unique request, operation, provider-request, snapshot, recorder,
  outcome, feedback, and measure IDs plus request/response/replay/database and
  recovery-state hashes instead of trusting summary booleans;
- upload six immutable content-addressed Actions artifacts from the read-only
  protected producer, then let a separate GitHub-hosted protected publisher
  independently revalidate and publish the six release assets;
- never write secret values to provenance or artifacts.

## Task 5: Run the protected pilot

Run three scenarios across `baseline`, `long_context`, and `aionis`: nine paid
chat calls total.

Scenarios:

1. branch recovery;
2. negative-transfer rejection;
3. summary-only inspection.

Pilot admission requires:

- Aionis action completion 3/3;
- zero failed direct-use and zero wrong direct-use;
- inspect coverage 100%;
- evidence-backed outcome, feedback, and measure coverage 100%;
- no worker/backlog/provider/model errors;
- exact operation replay after restart.

Any admission failure stops the paid run and produces a failed pilot receipt.

## Task 6: Run the bounded three-wave soak

Duration: 24 to 36 hours on one persistent Runtime volume with unique scopes.

Each wave runs the three scenarios across three groups and three repetitions,
plus deterministic golden/product/ordinary/single-agent/multi-agent loops.

- After wave 1: graceful container replacement.
- After wave 2: SIGKILL and replacement-container recovery.
- After wave 3: final health/backlog capture and offline SQLite verification.

Admission thresholds:

- product invariants: 100%;
- restart/recovery checks: 100%;
- wrong direct-use: 0;
- Aionis action completion: at least 26/27 and at least 8/9 per wave;
- outcome/feedback/measure coverage: 100%;
- durable exact replay: 100%;
- dead-letter, provider mismatch, exhausted work: 0;
- Aionis same-wave context must be shorter than Full History;
- every raw artifact and summary is content-addressed.

Metric denominators are frozen rather than inferred from whatever rows happen
to finish. `action_completion` uses exactly 27 Aionis trials (9 per wave).
`negative_direct_use` uses exactly the 9 declared negative-transfer trials; its
numerator counts unsafe direct uses, so admission requires `0/9`, not merely a
rounded percentage. Per-wave counts and aggregate sums must agree exactly.

This is bounded release evidence, not proof of universal model quality.

## Task 7: Open a new stable train

Only after Tasks 1-6 pass:

1. Create a new stable Runtime commit/version, expected v0.3.13.
2. Freeze a new Create package that defaults to v0.3.13.
3. Set `release-train.status` to `stable` and add the two content-addressed
   promotion-authority receipts.
4. Run exact-main CI and a fresh protected embedding smoke for the stable
   commit; candidate evidence is not reusable.
5. Run the no-override installer gate and exact-digest Docker gates.
6. Publish the immutable v0.3.13 tag/digest.
7. Move Docker `latest` only through the fixed stable path.
8. Publish a non-prerelease GitHub release and a new stable publication
   receipt. Do not mutate the v0.3.12 receipt.

## Stop conditions

Stop rather than promote when any of these is true:

- official Runtime workspace is unavailable or dirty in overlapping files;
- the external evaluation repository, exact authority commit, dedicated
  Actions-read token, or protected `bounded-soak`,
  `bounded-soak-publisher`, and `stable-release` environments are absent;
- the paid executor or exact-run evidence publisher remains intentionally
  unavailable;
- the OpenRouter V4 Pro credential/model cannot be bound exactly;
- any receipt hash, tag, commit, digest, platform, or model binding differs;
- the pilot fails admission;
- the soak crosses its time/cost bound;
- a Runtime invariant, recovery check, or backlog threshold fails;
- stable would require moving an existing immutable version tag;
- the installer needs an explicit override to select the proposed stable tag;
- complexity validation requires raising a ratchet.
